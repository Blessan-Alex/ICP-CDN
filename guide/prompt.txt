#### **Prompt 1.3: Build LRU Cache Logic**

Hey Cursor, our cache is currently just a HashMap. Let's make it smarter by implementing a Least Recently Used (LRU) eviction policy. This will ensure we keep the most relevant content in our limited cache space.

Please review the existing `CACHE` state and any `get`/`put` functions.

**Our Goal:** Augment our cache with an LRU mechanism. When the cache is full and a new item is added, the least recently used item should be automatically removed.

**Implementation Details:**

1.  **Add LRU Tracking State:**

      * Introduce a new `thread_local!` state variable: `LRU_QUEUE: RefCell<VecDeque<String>>`. We'll use a `VecDeque` as it's efficient for `push_back` (newest) and `pop_front` (oldest) operations.

2.  **Create a `touch_lru` Helper Function:**

      * This private function will take a `cid: &str` as input.
      * It should find the CID in the `LRU_QUEUE`, remove it from its current position, and then push it to the back of the queue, marking it as the most recently used.

3.  **Integrate LRU Logic into Cache Operations:**

      * **On Get:** In the function that retrieves an item from the cache, after successfully finding the item, call `touch_lru` with its CID.
      * **On Put:** In the function that adds a new item to the cache, after inserting it into the `HashMap`, push its CID to the back of the `LRU_QUEUE`.

4.  **Implement the Eviction Logic:**

      * In the "put" function, *before* adding the new item, check if the cache has reached its configured capacity (e.g., `MAX_CACHE_ITEMS`).
      * If the cache is full, use `lru_queue.pop_front()` to get the CID of the least recently used item.
      * Use this CID to remove the corresponding entry from the main `CACHE` `HashMap`.
      * Finally, proceed with adding the new item.

Let's refactor our cache to include this complete LRU eviction flow.

#### **Prompt 2.1: Implement Trustless, On-Chain Data Verification**

Hey Cursor, let's implement a critical security upgrade. Right now, when we fetch data from an IPFS gateway, we are trusting it to be honest. We need to eliminate this trust by cryptographically verifying all fetched content on-chain.

Please review the existing code that handles the `http_request` to IPFS gateways and the logic that caches the returned data.

**Our Goal:** Before caching any data fetched from IPFS, verify that its content hash matches the requested CID.

**Implementation Details:**

1.  **Add Hashing Dependencies:**

      * First, please add the following crates to our `Cargo.toml`. They are essential for parsing CIDs and performing SHA2-256 hashing.
        ```toml
        cid = "0.10"
        multihash = { version = "0.18", features = ["sha2"] }
        sha2 = "0.10"
        ```

2.  **Create a Verification Helper Function:**

      * Now, let's create a new private helper function: `verify_content_hash(cid_str: &str, data: &[u8]) -> Result<(), String>`.
      * This function must perform the following steps:
          * Parse the input `cid_str` into a `Cid` object.
          * Extract the hash algorithm and the expected hash digest from the parsed CID. We will primarily handle `sha2-256`.
          * Hash the input `data` byte slice using the same algorithm.
          * Compare the calculated hash digest with the expected digest from the CID.
          * Return `Ok(())` if they match perfectly, otherwise return an `Err` with a descriptive message like "Content hash does not match CID".

3.  **Integrate Verification into the Fetch Logic:**

      * Locate the asynchronous function that processes the response from the IPFS `http_request`.
      * After receiving the response body (`Vec<u8>`) and before calling the function to write it to the cache, insert a call to our new `verify_content_hash` function.
      * If the verification function returns an `Err`, you must **not** cache the data. Instead, log the error and return a failure status to the original caller.

Let's proceed with making our data ingestion process trustless.

#### **Prompt 2.2: Evolve to a Sustainable On-Chain SaaS Model**

Alright Cursor, time to turn our dCDN into a sustainable on-chain business. We're moving from a one-time fee model to a recurring storage rent model based on cycles.

Please get familiar with the `UserAccount` struct, the canister's state, and the `ic_cdk_timers` crate.

**Our Goal:** Implement a canister "heartbeat" that runs periodically to charge users cycles for the amount of data they are storing in the hot cache.

**Implementation Details:**

1.  **Update the `UserAccount` Struct:**

      * Please modify the `UserAccount` struct to include a new field: `last_billed_timestamp: u64`. This will help us calculate billing periods.

2.  **Establish the Canister Heartbeat:**

      * We need a task that runs automatically. In the canister's `post_upgrade` hook (and `init` hook for the first deployment), use `ic_cdk_timers::set_timer_interval` to set up a recurring timer.
      * Let's set it to run once every hour (`Duration::from_secs(3600)`). The timer should call a new public function named `charge_storage_rent`.

3.  **Implement the Core Billing Logic in `charge_storage_rent`:**

      * This function is the heart of our SaaS model. It must:
          * Get the current IC time via `ic_cdk::api::time()`.
          * Define a cost constant, e.g., `COST_PER_BYTE_PER_HOUR: u128`.
          * Iterate through all user accounts in our state.
          * For each user, find all the `CacheEntry` items they own (this might require adding an `owner: Principal` field to `CacheEntry`).
          * Calculate the `total_bytes_stored` for that user.
          * Calculate the `hours_since_last_bill` using the current time and the user's `last_billed_timestamp`.
          * Calculate the `rent_due = total_bytes_stored * COST_PER_BYTE_PER_HOUR * hours_since_last_bill`.
          * If `user.cycles_balance >= rent_due`, deduct the amount and update their `last_billed_timestamp`.
          * **Crucially:** If their balance is insufficient, trigger an eviction process: remove all of their files from the cache and LRU queue.

Let's build this on-chain subscription logic. Start by updating the necessary structs.

#### **Prompt 2.3: Build a Proactive & Intelligent Cache**

Hey Cursor, let's make our dCDN smarter. Instead of just reacting to requests, we want it to anticipate what content a user will need next and pre-fetch it.

Please review the main `get` endpoint and our state management.

**Our Goal:** Implement a system to track content access patterns and use that data to proactively pre-warm the cache with related content, reducing latency for the user.

**Implementation Details:**

1.  **Define Analytics Data Structures:**

      * Let's add two new `thread_local!` state variables for our analytics engine:
          * `CO_OCCURRENCE_GRAPH: RefCell<HashMap<(String, String), u64>>` - This will store a weighted graph where the key is a pair of CIDs and the value is how often they're requested together.
          * `USER_SESSION_LOG: RefCell<HashMap<Principal, Vec<String>>>` - A temporary log to track the sequence of requests within a short session for each user.

2.  **Log Access Patterns:**

      * Now, modify the primary endpoint that serves content (e.g., `http_request` or a `get` method). When a user requests a CID:
          * Get the caller's `Principal`.
          * Retrieve their recent request history from `USER_SESSION_LOG`.
          * For every previous CID in their session history, increment the counter in `CO_OCCURRENCE_GRAPH` for the pair `(previous_cid, current_cid)`.
          * Add the `current_cid` to the user's session log. Keep the session log short, maybe the last 5 items.

3.  **Implement Asynchronous Pre-warming Logic:**

      * In the same content-serving endpoint, immediately after logging the access:
          * Query the `CO_OCCURRENCE_GRAPH` to find the CID that is most frequently requested after the `current_cid`.
          * If you find a CID with a correlation score above a certain threshold (e.g., requested together more than 10 times):
              * Use `ic_cdk::spawn` to fire off a **non-blocking** background task.
              * This background task should call your internal `fetch_and_cache` function for the correlated CID. This is critical—it must not block or delay the response to the user's original request.
