Goal
Encrypt files client-side before Pinata upload.
No passwords; use keys bound to the user/device.
Decrypt in-browser for view/download.
Backend and Pinata see ciphertext only.
Approach overview
Generate a random per-file AES-GCM key.
Encrypt file in fixed-size chunks (e.g., 64KB) with IV counter.
Wrap the file key with the user’s public key (no password).
Upload ciphertext to Pinata; upload tiny metadata JSON with algorithm, IV scheme, chunk size, and the wrapped key.
On view/download, fetch ciphertext + metadata, unwrap file key using the private key (in browser), stream-decrypt and render.

    Option B (compact, sharing-friendly): X25519 + HKDF (e.g., @noble/curves/@noble/hashes)
Generate static X25519 key pair; derive a one-time AEAD key via ECDH + HKDF per wrap.
Similar wrapping/unwrapping, but requires a small lib; good for multi-recipient sharing.
Option C (strongest UX): WebAuthn resident keys
Use a platform authenticator (passkey) to hold the private key; the browser prompts on unwrap. Requires a WebAuthn flow; very secure and phish-resistant.
Recommendation: Start with RSA-OAEP Web Crypto (no external deps), then optionally add X25519 for multi-user sharing later.

This provides passwordless, end-to-end encryption: only the browser can decrypt; Pinata and backend only handle ciphertext and non-sensitive metadata.
ecurity notes
AES-GCM with unique IV per chunk (counter) provides integrity; never reuse IV+key pair.
Rotate or regenerate public key pairs per device if desired; allow export/backup of private key encrypted with a local passphrase if you need portability.
Consider CSP and disallow mixed content; keep metadata minimal (no PII).
For WebAuthn option, the private key remains in the authenticator; unwrap requires user presence/verification.
Backend hardening (so backend can’t see plaintext)
Accept only ciphertext uploads; do NOT accept plaintext upload when encryption is enabled.
Do not log request bodies; scrub storage/logs of sensitive headers.
If offering a server “download-decrypted” convenience route, ensure it only proxies ciphertext to the client; prefer pure client decrypt for zero-trust.
Enforce size limits, MIME checks, and rate limiting; reject oversized multipart early.
